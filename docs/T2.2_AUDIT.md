## 1. Paper specification (Figure 8 reconstruction)

Configurations are `(d, H, H′)`:
- `d` — current DyNetKAT process term.
- `H` — pending packet list (head = packet currently being processed).
- `H′` — handled packet list (head = most recently handled packet).

Labels (actions) `γ`:
```
γ ::= (σ, σ′) | x?r | x!r | rcfg(x, r)
```

Figure 8 rules (from paper text extraction, lines 565–671 of the PDF text)
reconstructed into standard premise/conclusion form. The PDF text scrambles
columns, so rule names and the textual description in §II-B (lines 425–448)
are the authoritative cross-check:

### (cpolX;) — packet flows through NetKAT policy
```
        σ′ ∈ ⟦p⟧(σ)        (i.e. σ maps to σ′ by NetKAT policy p)
------------------------------------------------------------
(p; q, σ :: H, H′)  →(σ,σ′)  (q, H, σ′ :: H′)
```
`σ` is removed from the head of `H`; `σ′` is consed onto `H′`. (§II-B line
431–434.)

### (cpolX) — recursion unfolding
```
        X ≜ p    (X defined as p)
        (p, H₀, H₁) →γ (p₀, H₀₀, H₁₀)
--------------------------------------------
        (X, H₀, H₁)  →γ  (p₀, H₀₀, H₁₀)
```
A recursive variable behaves according to its unique definition. (line 448.)

### (cpol⊕) left / (cpol⊕) right — non-deterministic choice
```
(p, H₀, H₀₀) →γ (p′, H₁, H₁₀)
--------------------------------
(p ⊕ q, H₀, H₀₀) →γ (p′, H₁, H₁₀)

(q, H₀, H₀₀) →γ (q′, H₁, H₁₀)
--------------------------------
(p ⊕ q, H₀, H₀₀) →γ (q′, H₁, H₁₀)
```
(§II-B line 436–439.)

### (cpol‖) left / (cpol‖) right — parallel component step
```
(p, H₀, H₀₀) →γ (p′, H₁, H₁₀)
------------------------------------
(p ‖ q, H₀, H₀₀) →γ (p′ ‖ q, H₁, H₁₀)

(q, H₀, H₀₀) →γ (q′, H₁, H₁₀)
------------------------------------
(p ‖ q, H₀, H₀₀) →γ (p ‖ q′, H₁, H₁₀)
```
The "inactive" operand is preserved. (line 439–440.)

### (cpol!?) / (cpol?!) — synchronization (rcfg)
```
(q, H, H′) →(x?r) (q′, H″, H‴)       (s, H, H′) →(x!r) (s′, H″, H‴)
-------------------------------------------------- (cpol!?)
(q ‖ s, H, H′) →(rcfg(x,r)) (q′ ‖ s′, H″, H‴)

(s, H, H′) →(x!r) (s′, H″, H‴)       (q, H, H′) →(x?r) (q′, H″, H‴)
-------------------------------------------------- (cpol?!)
(q ‖ s, H, H′) →(rcfg(x,r)) (q′ ‖ s′, H″, H‴)
```
Synchronization of matching send/receive on channel `x` with the same policy
`r` collapses to a single `rcfg(x,r)` step; H/H′ are unchanged across the
whole rule. (line 444–447.)

### (cpol;‡) etc. — NOT part of Figure 8 core
The `rcfg(x,z); p → p` rule is Eq. (4), introduced later in §III (line 781).
The `T` and `|` merge rules (Eq. 5) appear at lines 849–892, after the
projection/restriction discussion, and are part of the *extended* operators
(T3.4), not the core T2.2 figure. This audit treats them as out of scope.

## 5. Packet-flow rule dependency on NetKAT semantics

The `(cpolX;)` rule depends on the NetKAT denotational semantics
`⟦N⟧(σ)` returning the output packet set `σ′ ∈ ⟦N⟧(σ)`. The NetKAT layer is
**partially** present and is the only relevant input available:

- `Semantics.lean:61-71` defines `Semantics : NetKAT → CtxPkt → CtxPkt → Prop`.
  ✅ (exists; this is the relation `⟦N⟧(σ,σ′)`)
- `Semantics.lean:74-75` defines `eval N σ = { q | Semantics N σ q }` ✅.
- `Semantics.lean:51-53` defines `StarClosure` for `⟦N*⟧` ✅.

**However**, the repo lacks the DyNetKAT *extended* syntax `N; D`, so there
is no `DyNetKAT` inductive type to host the rule premise. T2.2's
`(cpolX;)` rule is structurally inseparable from the `;` operator on
DyNetKAT processes, which belongs to **T2.1** (not implemented — see
`FEATURE_GAP_ANALYSIS.md:890`).

**Discrepancy D7** (dependency missing): `(cpolX;)` requires the DyNetKAT
`N; D` sequencing constructor. That constructor is part of T2.1, which has
zero implementation. The NetKAT `Semantics` relation exists but there is
nothing to apply it *to* at the DyNetKAT layer.

## 9. Verdict

**T2.2: BLOCKED.**

Nothing in the Figure 8 specification — configurations (`D1`), actions/labels
(`D3`/`D4`), or any transition rule (`D5`) — is present in the Lean repo.
The only relevant prerequisite, the NetKAT denotational relation
`Semantics`, exists (`Semantics.lean:61-71`); but it cannot be applied
because the DyNetKAT process syntax that would carry the `(cpolX;)` rule is
absent (`D7`, a T2.1 gap). The NetKAT layer compiles cleanly, so there is no
blocking build error, but the DyNetKAT operational layer is entirely
absent. No part of T2.2 can pass while T2.1 (DyNetKAT syntax) and the
`Step`/`Config`/`Action`/`Channel` definitions remain missing.
